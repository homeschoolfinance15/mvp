## Confirmed defects

### D1 — Submitted feedback is available to non-admin authors

**High; FDB-09, FDB-12, FDB-13, QLT-05; section 9 confidentiality.**

Reproduction: a verified non-admin attendee submits event feedback. Calling `my_event_feedback(event)` returns the saved answer (HTTP 200). In the browser, **Change my feedback** repopulates the submitted text. Calling `export_my_data()` also returns it in `event_feedback_i_wrote`. The export implementation additionally includes `peer_feedback_i_wrote`.

Expected: under this brief, authors receive confirmation/progress but cannot read submitted reviews, including through downloads. Actual: authors can read them through both the feedback UI/API and the account export. Another attendee's own `my_event_feedback` call returned no answers; this is not evidence of cross-user disclosure.

Sources: [feedback readback RPC](../../supabase/migrations/20260924200301_my_event_feedback.sql), [account export](../../supabase/migrations/20260924102101_account_deletion_and_export.sql), [reviseEvent and Change my feedback](../../src/routes/events/Feedback.tsx). The readback migration explicitly cites “Decision 19”; this remains a conflict with the supplied brief unless the user explicitly revises that brief.

Evidence: [browser screenshot](uat-evidence/feedback-readback.png), independent result assertions. Existing acceptance tests only checked direct table reads and missed these RPC/export paths.

### D2 — Editing a question changes the meaning shown for historical answers

**High; FDB-16; section 9 original questions and meaning.**

Reproduction: create a test event question, store an answer to it, then PATCH that same question's wording as an administrator. The PATCH succeeds (HTTP 200). Joining the saved answer to its question now returns the new wording, not the wording asked when the answer was submitted. The administrator screen resolves wording from the current question row too.

Expected: past answers retain their original question/version and meaning. Actual: `question_id` references a mutable question; a version column alone does not enforce immutability. The submission RPC also accepted a new answer to an inactive question (HTTP 204), an additional version-lifecycle weakness.

Sources: [question schema and write grants](../../supabase/migrations/20260916000007_feedback.sql), [submission RPCs](../../supabase/migrations/20260923000501_attendee_event_guards.sql), [admin wording lookup](../../src/routes/admin/AdminEvent.tsx). Test used its own question, never edited the five real seeded questions.

### D3 — Later event-update flow does not provide the required preview

**High; ORG-10, EML-03, EML-04, EML-10.**

Reproduction: open an event's Emails page → **Send an update to attendees**. The modal provides a subject, free text, and **Send it**, but no rendered email preview, actual recipient count, or structured latest saved changes. The request contains no `changed_details` snapshot, so this path cannot perform the expected preview-versus-current-details comparison.

Expected: a later send action still previews the latest changes and intended audience before sending. The event editor's separate save-and-notify flow does not cover this missing later-action behavior.

Source: [UpdateModal](../../src/routes/manage/EventEmails.tsx). Evidence: [update dialog screenshot](uat-evidence/update-dialog.png). The screenshot and source demonstrate this defect independently of mail delivery availability.

### D4 — “Optional” email subject is rejected by the endpoint

**Medium; EML-03, QLT-02.**

Reproduction: leave Subject blank in the same modal. The hint promises that the event title will be used. The client sends `subject: null`; the endpoint requires a nonblank subject and returns HTTP 400, “An update needs a subject.” Observed directly in the earlier local run. Later runs returned HTTP 503 from an intermittently unavailable Edge Runtime; those 503s are environment blocks, not additional proof of D4.

Sources: [optional subject hint and payload](../../src/routes/manage/EventEmails.tsx), [endpoint validation](../../supabase/functions/event-email/index.ts).

### D5 — Earlier rescheduling can suppress the initial feedback email permanently

**High; FDB-03, FDB-06, FDB-15, EML-01, EML-06.**

Reproduction: publish a future event, record attendance, then correct its dates so the event has ended and its configured feedback opening is in the past. The unsent `feedback_open` message becomes `skipped`, with `sent_at: null`. Correct another registered participant's attendance after this change. No scheduled, queued or sent feedback request is created or restored; the initial request remains skipped.

Expected: saved scheduling rules and attendance corrections make the initial request available without duplicating a previous send. Skipping already-past **pre-event reminders** is explicitly required, but that must not silently discard the initial feedback request. Actual: the scheduling function uses the same skip behavior for feedback, and the late-recipient function only attaches to a scheduled message or a previously sent one. Neither handles this never-sent skipped message.

Sources: [schedule_event_messages](../../supabase/migrations/20260924100101_reminder_orphans.sql), [add_late_feedback_recipient](../../supabase/migrations/20260916000019_transactional_emails.sql). Evidence: final assertion in [concurrency-results.json](uat-evidence/concurrency-results.json).

## Additional gaps and limits

- **ORG-05 — permission design gap:** named cohost membership is itself the broad `hosts_event()` authorization. The hosting-team UI has no separate display-only host/staff capability assignment. The brief explicitly distinguishes being named from permitted editing, guest/contact, communications, scanning, and payment actions. Existing event isolation passes, but this distinction has not been demonstrated. Source: `event_hosts`, `hosts_event()`, and EventEditor's hosting team.
- **ATT-01 / QLT-01 — device coverage gap:** scanning depends on native `BarcodeDetector` with a typed-code fallback. The tested Chromium had no detector. Camera decoding on an actual supported phone was not demonstrated. Do not claim iPhone/Safari scanning works from these tests; manual entry is not proof of camera scanning.
- **QLT-10 — missing acceptance targets:** no concrete capacity, sales-throughput, or concurrent-scanner operating target was located in the implementation contract/operating docs. Local race correctness passes; production load, latency, network interruption, and target verification remain outstanding.
- **Actual money and email:** no real Stripe test-mode payment/refund/OAuth, actual processor fees, dispute handling, delivered attendee email, closed-dashboard automatic dispatch, or failed-provider-send retry was demonstrated. Simulator and source checks do not satisfy those complete acceptance examples.
- **Operations/transition:** production migration state, existing-data reconciliation, administrator replacement, account-to-network conversion preserving all event history, and the network-signup waitlist were not exercised end to end. Deployment/payment/email docs exist; some README/deployment statements describe earlier behavior and should not be treated as verified current operating instructions.
